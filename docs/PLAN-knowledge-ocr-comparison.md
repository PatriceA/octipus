# Implementation Plan: Knowledge Upgrade, Document OCR, competitor Comparison

## Decision Log

- **OpenViking rejected**: Requires Python + Go + C++ as external Docker service. Breaks embedded/standalone mode ("clone + bun run dev" must work). Instead, we improve our existing pgvector system by borrowing OpenViking's best ideas.
- **Hybrid search**: Add PostgreSQL tsvector (BM25-style full-text) alongside pgvector cosine similarity. Both built into PostgreSQL — no new dependencies.
- **Tiered content**: Implement L0 (abstract) / L1 (overview) columns inspired by OpenViking, generated by our existing LLM.
- **OCR**: glm-ocr model already downloaded to ollama2 (2.2GB). Access via ollama2:11435.
- **competitor**: Real project at github.com/competitor/competitor. Key gaps identified: unified cross-channel messaging, Teams webhook stub, document processing in Slack/Teams.
- **Channels**: Not expanding beyond current set (Telegram, WebChat, WhatsApp, Slack, Teams). Slack is complete. Teams has a stub webhook — needs fixing.
- **Image generation**: competitor wraps Google Gemini / FAL / DALL-E. We could add via ComfyUI/NanoBanana but not a priority — skipping for now.
- **Unified cross-channel messaging**: competitor's best feature — single `message` tool with action-based dispatch. We already have UMI (`src/channels/interface.ts`) with `send(channelType, channelId, response)`. Need to expose this as an agent tool.

## Phase 1: Knowledge Base Upgrade (Hybrid Search + Tiered Content)

### What to implement

**1a. Add hybrid search (tsvector + pgvector)**

- **Migration** (`src/db/migrations/0015_hybrid_search.sql`):
  ```sql
  ALTER TABLE embeddings
    ADD COLUMN content_tsv tsvector
    GENERATED ALWAYS AS (to_tsvector('english', content)) STORED;
  CREATE INDEX embeddings_content_tsv_idx ON embeddings USING GIN (content_tsv);
  ```
- **Schema** (`src/db/schema/embeddings.ts`):
  - Add `customType` for tsvector (read-only, auto-generated column)
  - Add `tsRank()` and `tsMatch()` SQL helpers
- **EmbeddingService** (`src/core/rag/embeddings.ts`):
  - Add `hybridSearch(query, limit, sourceType?, alpha?)` method
  - Uses CTE with min-max normalization: `(1-alpha) * ft_norm + alpha * vec_norm`
  - Falls back to FTS-only if embedding generation fails
  - Keep existing `search()` method as fallback
- **Knowledge tool** (`src/tools/knowledge/index.ts`):
  - Update `search_knowledge` to use `hybridSearch()` instead of `search()`
  - Add optional `mode` parameter: `'hybrid'` (default), `'semantic'`, `'keyword'`

**1b. Add tiered content (L0 abstract / L1 overview)**

- **Migration** (`src/db/migrations/0015_hybrid_search.sql` — same file):
  ```sql
  ALTER TABLE embeddings ADD COLUMN abstract TEXT;
  ALTER TABLE embeddings ADD COLUMN overview TEXT;
  ```
- **Schema** (`src/db/schema/embeddings.ts`):
  - Add `abstract` (nullable TEXT, ~100 tokens) and `overview` (nullable TEXT, ~500 tokens)
- **EmbeddingService** (`src/core/rag/embeddings.ts`):
  - Add `generateAbstract(content)` — calls LLM: "Summarize in 1-2 sentences"
  - Add `generateOverview(content)` — calls LLM: "Summarize key points in a paragraph"
  - Update `indexText()` to generate abstract for each chunk (fire-and-forget, non-blocking)
  - Overview generated on-demand or for large documents only
- **Search optimization**: Return abstracts in search results first. Load full content only when agent requests it via a new `read_knowledge` tool action.

**1c. Add `read_knowledge` action**

- **Knowledge tool** (`src/tools/knowledge/index.ts`):
  - New action `read_knowledge`: takes `id` parameter, returns full L2 content
  - Search results now return `{ id, abstract, similarity, sourceType }` (lightweight)
  - Agent reads full content only for relevant results → token savings

## Phase 2: Document OCR & File Upload System

### What to implement

**2a. File upload API endpoint**

- **Route** (`src/api/routes/documents.ts` — NEW):
  - `POST /api/documents/upload` — multipart/form-data
  - Accepts: images (png, jpg, tiff, bmp, webp), PDFs, office docs
  - Max file size: 50MB per file
  - Multi-upload: accepts multiple files in one request
  - Returns: `{ documents: [{ id, filename, status: 'queued' }] }`
  - Auth: Bearer JWT (same as other routes)

- **Elysia multipart setup** (`src/api/server.ts`):
  - Register documents route group
  - Elysia handles multipart natively via `t.File()` schema

**2b. Document storage (filesystem + DB)**

- **DB table** (`src/db/schema/documents.ts` — NEW):
  ```typescript
  export const documents = pgTable('documents', {
    id: uuid('id').primaryKey().defaultRandom(),
    userId: text('user_id').notNull(),
    filename: text('filename').notNull(),
    originalName: text('original_name').notNull(),
    mimeType: text('mime_type').notNull(),
    size: integer('size').notNull(),
    category: text('category'),           // invoices, contracts, reports, etc.
    ocrText: text('ocr_text'),            // extracted text
    summary: text('summary'),             // LLM-generated summary
    status: text('status').notNull().default('queued'),  // queued, processing, completed, failed
    storagePath: text('storage_path').notNull(),
    metadata: jsonb('metadata').$type<Record<string, unknown>>().default({}),
    createdAt: timestamp('created_at').defaultNow().notNull(),
    processedAt: timestamp('processed_at'),
  });
  ```

- **Filesystem layout**:
  ```
  workspace/documents/
    uncategorized/       # initial landing zone
    invoices/
    contracts/
    reports/
    correspondence/
    technical/
    receipts/
    legal/
    medical/
    financial/
    other/
  ```

- **Migration** (`src/db/migrations/0016_documents.sql` — NEW)

**2c. OCR processing pipeline**

- **Processor** (`src/core/documents/processor.ts` — NEW):
  - Queue-based: process one document at a time (prevent ollama2 overload)
  - Pipeline per document:
    1. **OCR**: Send image/PDF to glm-ocr via ollama2 (`POST http://ollama2:11435/api/generate` with image)
    2. **Categorize**: Ask LLM to classify into category based on extracted text
    3. **Move file**: From `uncategorized/` to `{category}/`
    4. **Summarize**: Ask LLM to generate summary
    5. **Index**: Store extracted text + summary in knowledge base (embeddings table)
    6. **Update DB**: Set status=completed, category, ocrText, summary
  - For PDFs: extract pages as images, OCR each page, concatenate
  - For text-based files (already text): skip OCR, just categorize + summarize

- **Queue** (`src/core/documents/queue.ts` — NEW):
  - Simple in-memory queue with concurrency=1
  - Processes documents sequentially (ollama2 can only handle one at a time)
  - Emits progress events via orchestrator event system

**2d. Channel file handling**

- **Telegram** (`src/channels/telegram/index.ts`):
  - When receiving photo/document attachment: download file, save to workspace/documents/uncategorized/
  - Create document DB record with status='queued'
  - Enqueue for processing
  - Reply: "Document received, processing..."

- **WhatsApp** (`src/channels/whatsapp/index.ts`):
  - Same pattern: download media via Graph API, save, enqueue

- **Slack** (`src/channels/slack/index.ts`):
  - Already has attachment handling (lines 210-223): files from `file.url_private`
  - Add: download file to workspace/documents/uncategorized/, create document record, enqueue
  - Note: Slack file URLs require auth header (`Authorization: Bearer xoxb-...`)

- **Teams** (`src/channels/teams/index.ts`):
  - Already extracts attachments from `activity.attachments` (lines 120-134)
  - Add: download file from `attachment.contentUrl`, save, enqueue
  - **Critical fix needed**: `processActivity()` is a stub (lines 59-72) — Teams can't receive inbound messages. Need to add webhook route at `POST /api/channels/teams/webhook` that bridges Elysia request to Bot Framework adapter.
  - Also missing: link command equivalent

- **WebChat** (`src/api/websocket.ts` + `web/components/chat/prompt-input.tsx`):
  - Frontend: extend accepted file types to include PDF, images (already partially supported)
  - Backend: when WebSocket message has attachments, save to filesystem, enqueue
  - Add upload progress indicator in UI

**2e. Document management tool**

- **Tool** (`src/tools/documents/index.ts` — NEW):
  - `list_documents` — list documents with optional category/status filter
  - `get_document` — get document details + OCR text + summary
  - `search_documents` — search via knowledge base (uses hybrid search)
  - Available to all agent roles that have `knowledge` tool

## Phase 4: Unified Cross-Channel Messaging Tool

### Context

competitor's best feature: a single `message` tool that lets agents send messages to any channel. Instead of agents only replying in the channel that triggered them, they can proactively reach out on Telegram, Slack, Teams, WhatsApp — all through one tool interface.

We already have `UnifiedMessageInterface` (`src/channels/interface.ts`) with `send(channelType, channelId, response)` and `getConnectedChannels()`. The UMI is used internally by hook actions (`src/hooks/actions.ts`) for notifications. We just need to wrap it as an agent tool.

### What to implement

**4a. Messaging tool** (`src/tools/messaging/index.ts` — NEW)

Actions:
- `send_message` — send a message to a specific channel + target
  - Parameters: `channel` (telegram/slack/teams/whatsapp/webchat), `target` (channel/user ID), `message` (text), `reply_to?` (thread/message ID)
  - Uses `getUMI().send(channel, target, { content: message })`
- `list_channels` — list connected channels with their status
  - Returns: `[{ type, name, connected, capabilities }]`
- `list_contacts` — list known users with their channel bindings
  - Queries user table for channel bindings, returns `[{ userId, userName, channels: [{ type, channelUserId }] }]`
  - Enables: "send a message to Patrice on Telegram" → resolve user → find Telegram binding → send

**4b. Dynamic capabilities**

- Each channel declares what it supports (text, images, threads, reactions)
- Tool description built at runtime listing available channels and their features
- Similar to competitor's dynamic schema but simpler — we don't need 40 actions, just send/list

**4c. Channel target resolution**

- **By user name**: Look up user in DB → find channel binding → resolve target ID
- **By channel ID**: Direct send (for agents that already know the target)
- **By session context**: Default to the originating channel of the current session
- **Broadcast**: Send to all verified bindings of a user (for notifications)

**4d. Integration with agent roles**

- Add `messaging` tool to roles that need proactive communication: `general`, `communication`, `pm`
- Orchestrator meta-tools can use it for status updates and approvals
- Hook actions already use UMI — this just makes it available to agents too

### Files to create/modify

| File | Action |
|------|--------|
| `src/tools/messaging/index.ts` | NEW — unified messaging tool (send_message, list_channels, list_contacts) |
| `src/tools/index.ts` | MODIFY — register messaging tool |
| `src/core/orchestrator/roles.ts` | MODIFY — add messaging tool to relevant roles |
| `src/channels/interface.ts` | MODIFY — add getCapabilities() to BaseChannel |
| `mcp-server/src/tools/messaging.ts` | NEW — expose via MCP |

### Verification

1. `bunx tsc --noEmit` — clean build
2. Agent with messaging tool calls `list_channels` → sees connected channels
3. Agent calls `send_message` with channel=telegram, target=userId → message delivered
4. Agent calls `list_contacts` → sees users with their channel bindings
5. Hook notification uses same tool interface
6. Cross-channel: agent triggered from webchat sends update to Telegram

### Anti-patterns

- Do NOT expose channel credentials or internal IDs to the LLM
- Do NOT allow sending to arbitrary external targets — only known users/channels
- Do NOT build 40 actions like competitor — keep it simple: send, list channels, list contacts
- Do NOT duplicate the existing hook notification logic — reuse UMI.send()

1. **Phase 1** (Knowledge Upgrade) — Foundation. Other phases depend on improved search.
2. **Phase 2** (Document OCR) — Depends on Phase 1 for indexing OCR'd content. Includes Teams webhook fix + Slack/Teams document processing.
3. **Phase 4** (Unified Messaging) — Can run in parallel with Phase 2. Independent of knowledge changes.
4. **Phase 3** (Comparison Tests) — Last. Tests all new capabilities from Phases 1-4.
