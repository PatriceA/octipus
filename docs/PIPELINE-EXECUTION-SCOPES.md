# Pipeline approvals and host execution

A run permission profile belongs to its owner, session and workspace. It is reloaded from the pipeline record for each decision and survives pause/resume and backend restarts. Explicit DENY rules, shared-space restrictions and credential boundaries still apply.

For shell calls, authorization resolves the effective cwd using the same code as execution: an explicit directory, a relative path against the project/workspace, or the shell's actual default. It never substitutes the profile's repository for an unknown execution directory. Prefer an explicit absolute `cwd` in the target repository. A profile is not an SSH connection: a remote command remains an SSH command and never becomes local Docker execution.

An entry in `commands` authorizes that fixed command within the approved repositories, including personal-session flow-guard consent. Narrow read-only verification matching also permits the same canonical GET URL with timeout/output-only changes, or the same SSH host and explicit Compose file with batch/timeout or table/JSON output changes. Registered-shell `cd ... && docker compose ps` shorthand is rewritten to the explicitly approved `-f .../compose.yaml` command and discloses requested/executed text; it never executes default-file or override discovery. Native Bash cannot claim that rewrite. Changed targets, noncanonical paths, escaping, shell additions, headers, request bodies, uploads, redirects and SSH forwarding/proxy settings do not qualify. Package-manager and public-host command families do not grant flow-guard consent for arbitrary data egress. Overnight refusals identify the effective directory or command/flow rule, pipeline id, profile revision and approval timestamp. Refused operations have not executed; they have no process exit code.

Forwarded pipeline approval prompts wait up to one hour. Ordinary tool permission requests remain durable until answered or the worker is stopped. Continuing the same saved attempt under its approved profile does not add a replay prompt for known completed journal actions. A deliberate rewind, missing/legacy journal evidence, active actions and uncertain outcomes retain recovery review. Exact remembered decisions retain the boolean data posture recorded when the original approval prompt was created, across stages and restarts. Newly gained labels require fresh consent; labels and historical refusal records are never cleared by approval. `get_cli_run_context` exposes redacted approved commands only to the scoped stage; a root context does not inherit its child’s execution permission. A timeout can leave effects; neither resume nor a run profile proves those effects absent.

## Shared browser runtime

All bubblewrap/firejail sandbox jobs receive read-only mounts of installed host Playwright runtime directories (browser profiles stored alongside the cache are excluded), independently of `hostServices`. Foreground, background and stage shells use the same default cache; an operator can configure an absolute server-side `PLAYWRIGHT_BROWSERS_PATH`. No browser is installed or downloaded automatically. A project still needs a compatible revision already provisioned there.

Before a long showcase, run a small Playwright launch/close smoke check through the same registered shell and project dependency version. Shell launch failures include `environmentDiagnostic` distinguishing an absent host cache, a missing revision and an existing host executable inaccessible to the job. Background job logs retain the original launch error; inspect their expected revision against the shared cache before retrying. Browser smoke success is not evidence that the full application showcase passed.

## Dedicated local Docker Compose lifecycle

A shell without `hostServices` lacks the Docker socket; this says nothing about the host daemon. Use permitted `docker__list_containers`, `docker__exec_command` and `docker__compose_project` instead of concluding Docker is unavailable.

For physical Android testing, `hostServices` grants host networking (including the existing ADB server on localhost:5037) and direct Linux USB device access at `/dev/bus/usb`, with USB sysfs topology mounted read-only. The same grant reaches foreground shells, background shells and verification gates. A plain `network: true` shell call can reuse the host ADB server without direct USB access. SDK visibility alone does not grant device access; verify `adb devices -l` inside the testing runtime. Host USB permissions and phone authorization still apply.

`docker__compose_project` accepts `operation` (`status`, `up`, `logs`, `down`), an explicit `project`, an absolute approved `cwd`, an optional repository-relative `file` (default `compose.yaml`), `approvedPorts`, `approvedBindPaths`, `build`, `forceRecreate`, optional `services` and an execution `timeout` in milliseconds. Example:

```json
{"operation":"up","project":"composer-test","cwd":"/approved/repository","approvedPorts":[4300,4301],"approvedBindPaths":["/opt/app/data"],"timeout":600000}
```

The normal Docker `compose` permission/approval applies to the full request, including port and host bind-path consent. Existing host paths listed in `approvedBindPaths` may be bound into containers; sources are resolved to canonical paths and must stay within the explicitly approved roots. Cleanup preserves that host data. `up` creates services and waits for health; status and logs are project-scoped. Results include exit status and stdout/stderr, health output where applicable, and cleanup success for `down`. Cleanup removes project orphans, checks for remaining containers, and preserves volumes and images. Permanent project reservations bind the local daemon project to its user, workspace and repository, including after down preserves volumes. An approved lifecycle request can register an existing project in that execution scope after its container working-directory labels match the approved repository. A registered project never transfers to a different user, workspace or repository. Status/log reads enforce the same ownership. A project name already attached to another working directory is refused. External resources, custom container names, host privileges, unapproved bind mounts and published ports are unsupported. Repository-local inline builds and service env files are supported. Build contexts, Dockerfiles and env files must resolve inside the approved repository; remote contexts, interpolated source paths, build SSH/secrets/host privileges, imports and host secret/config-file sources are unsupported. Source YAML and normalized configuration are captured into private temporary snapshots before lifecycle execution; the repository file is not reread. An existing repository-local `.env` is used for initial Compose interpolation; configuration output is kept private. Lifecycle execution uses the captured configuration with further `.env` loading disabled. Missing required configuration remains a configuration failure, not an approval denial. Approved host bind directories and their ancestors must remain stable during execution, including when repository scripts or background jobs can modify them. Canonical checks do not make these paths race-proof against concurrent agent or host filesystem changes. Repository contents remain executable configuration and must be trusted/reviewed; this tool is not a sandbox for malicious Dockerfiles or images.

For a rebuild/restart use `operation: "up", build: true, forceRecreate: true`; optionally select service names with `services`. `down` always targets the named project as a whole and preserves volumes.

Compose is currently refused under enforced per-user Docker isolation; existing isolated container operations remain available. No shell socket is granted as a fallback. Remote stacks still require independently approved SSH commands and their deployment backup/rollback checks.
